# sdp — 시스템 설계 레퍼런스

## 설계 진행 4단계 (항상 이 순서)

1. **요구사항 고정** — 기능 요구 + 비기능 요구(트래픽, 데이터량, 읽기/쓰기
   비율, 지연 목표, 일관성 요구). 숫자 없으면 추정해서라도 적는다.
2. **고수준 설계** — 컴포넌트와 데이터 흐름을 그린다. 이 단계에서 기술
   이름(Redis, Kafka)이 아니라 역할(캐시, 로그 큐)로 말한다.
3. **핵심 상세화** — API 계약, 데이터 모델, 가장 위험한 컴포넌트 내부.
4. **병목 확인 후 확장** — 측정/추정으로 병목을 특정한 뒤에만 캐시, 샤딩,
   큐, 복제를 추가한다.

## 철칙

- **조기 확장 금지.** 로드밸런서·샤딩·마이크로서비스는 규모가 증명되기
  전에는 비용만 늘린다. 단일 프로세스 + 좋은 모듈 경계가 먼저다.
- **모든 선택은 트레이드오프.** "무엇을 얻고 무엇을 포기하는가"를 항상
  한 쌍으로 말한다.
- **상태를 줄여라.** 무상태 컴포넌트는 공짜로 수평 확장된다. 상태는
  한곳(DB/캐시/큐)에 모으고 나머지를 무상태로.
- **소규모 프로젝트 적용**: 관심사 분리, 느슨한 결합, 단일 진입점,
  파일/메시지 계약 기반 단계 합성 — 이 원칙만 가져오고 인프라 패턴은
  가져오지 않는다.

## 빠른 결정 프레임워크

| 증상 | 1차 처방 | 그다음 |
|---|---|---|
| 읽기 느림 | 인덱스, 쿼리 튜닝 | 캐시 → 읽기 복제본 |
| 쓰기 느림 | 배치/비동기화 | 파티셔닝 → 샤딩 |
| 요청 폭주 | 레이트리밋, 큐잉 | 수평 확장 + LB |
| 느린 외부 호출 | 타임아웃 + 재시도 | 서킷브레이커, 비동기화 |
| 단일 장애점 | 복제본 + 헬스체크 | 자동 failover |
