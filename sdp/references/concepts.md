# 시스템 설계 핵심 개념 (system-design-primer 증류)

## 성능 vs 확장성

- 성능 문제: 한 사용자에게도 느리다. 확장성 문제: 한 명이면 빠른데 부하가 늘면 느려진다.
- 확장성 = 리소스를 더하면 비례해서 처리량이 늘어나는 성질.

## 지연시간 vs 처리량

- Latency: 요청 하나의 소요 시간. Throughput: 단위 시간당 처리 건수.
- 일반 목표: 허용 가능한 latency 안에서 throughput 최대화.

## CAP 정리

네트워크 분단(P)은 피할 수 없으므로 실질 선택은 CP vs AP.

- **CP (일관성 우선)**: 분단 시 오류/타임아웃 허용. 원자적 읽기·쓰기가 필요할 때.
- **AP (가용성 우선)**: 분단 시 최신이 아닐 수 있는 데이터라도 응답. eventual consistency 허용 업무에.

## 일관성 패턴

- **Weak**: 쓰기 후 읽기가 반영 안 될 수 있음 (VoIP, 게임 실시간 상태).
- **Eventual**: 비동기 전파, 결국 반영 (DNS, 이메일). 고가용성 시스템의 기본기.
- **Strong**: 쓰기 즉시 모든 읽기에 반영 (트랜잭션, 파일시스템). 가용성 희생.

## 가용성 패턴

- **Fail-over**: active-passive(대기 승격) / active-active(부하 분산 겸용). 단점: 하드웨어 추가, 전환 중 쓰기 유실 가능.
- **Replication**: master-slave / master-master (DB 절 참조).
- 직렬 구성 가용성 = 곱 (99.9% × 99.9% = 99.8%), 병렬 구성 = 1 - (1-A)² (99.9% 둘이면 99.9999%).

## DNS / CDN

- DNS: 도메인을 IP로. 라우팅 정책(가중치, 지연 기반, 지리 기반). 캐시 TTL.
- CDN: 정적(때로 동적) 콘텐츠를 사용자 가까이에서 서빙.
  - **Push CDN**: 갱신 때 직접 업로드. 트래픽 적고 변경 드문 사이트.
  - **Pull CDN**: 첫 요청 때 원본에서 끌어와 캐시. 트래픽 많은 사이트.

## 로드밸런서 vs 리버스 프록시

- LB: 여러 서버에 요청 분산, 헬스체크, SSL 종료, 세션 유지. L4(전송계층) / L7(애플리케이션 계층, 내용 기반 분기).
- 리버스 프록시: 서버가 하나여도 유용 (보안, 캐시, 압축, 정적 서빙).
- 수평 확장의 전제: 서버 무상태화(stateless), 세션은 중앙 저장소(DB/캐시)로.

## 애플리케이션 계층

- 웹 계층과 애플리케이션 계층 분리 — 독립 확장 가능.
- **마이크로서비스**: 작은 독립 서비스 모음. 서비스 디스커버리(Consul, etcd 등) 필요.
- 단점: 배포·운영 복잡도 증가. 규모가 정당화할 때만.

## 데이터베이스

**RDBMS 확장 순서** (쉬운 것부터):

1. 튜닝: 인덱스, 슬로우 쿼리, 스키마 정규화 수준 조정
2. **Master-slave replication**: 읽기 분산. 복제 지연 주의.
3. **Master-master**: 쓰기 분산, 충돌 해결 필요.
4. **Federation**: 기능별 DB 분리 (users DB, products DB).
5. **Sharding**: 데이터를 수평 분할. 핫스팟(celebrity problem), 리밸런싱, 조인 어려움.
6. **Denormalization**: 읽기 성능 위해 중복 허용. 쓰기 비용 증가.

**NoSQL 종류**: key-value(Redis) / document(MongoDB) / wide-column(Cassandra) / graph(Neo4j).

**SQL 선택 근거**: 구조화 데이터, 엄격한 스키마, 트랜잭션, 조인. **NoSQL 선택 근거**: 유연한 스키마, 대량 쓰기 처리량, 반정형 데이터, 수평 확장 우선.

## 캐시

- 위치: 클라이언트, CDN, 웹서버, DB 자체, 애플리케이션 캐시(Redis/Memcached).
- 전략:
  - **Cache-aside**: 앱이 미스 시 DB에서 읽어 캐시에 적재. 가장 흔함. 미스 3연산 비용, 스테일 가능.
  - **Write-through**: 쓰기를 캐시 경유로 DB까지 동기 반영. 읽기 빠름, 쓰기 느림.
  - **Write-behind**: 캐시에 쓰고 비동기로 DB 반영. 빠르지만 유실 위험.
  - **Refresh-ahead**: 만료 전 선제 갱신. 예측 정확해야 이득.
- 무효화가 가장 어렵다 — TTL부터 시작하고 필요하면 정교화.

## 비동기 처리

- **Message queue** (RabbitMQ, SQS, Redis): 요청을 큐에 넣고 즉시 응답, 워커가 나중에 처리.
- **Task queue** (Celery): 스케줄·백그라운드 작업.
- **Back pressure**: 큐가 차면 유입 제한 (503 + 재시도), 큐 무한 성장 방지.
- 느린 연산은 인라인으로 하지 말고 뒤로 뺀다.

## 통신

- TCP: 연결 지향, 순서·재전송 보장. UDP: 비보장, 낮은 지연 (스트리밍, VoIP).
- REST: 리소스 중심, 무상태, HTTP 동사. RPC(gRPC 등): 행위 중심, 내부 서비스 간 고성능 통신.
- 공개 API는 REST, 내부 고빈도 호출은 RPC가 흔한 균형.

## 보안 기초

- 전송 구간·저장 데이터 암호화. 모든 입력 살균/검증 (SQL injection, XSS 방지).
- 최소 권한 원칙.
