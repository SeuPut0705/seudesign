# 비동기 처리

## 언제 큐를 쓰나

- 요청 처리 중 느린 작업(영상 인코딩, 이메일, 외부 API)이 끼어 있을 때 —
  큐에 넣고 즉시 응답, 워커가 소비.
- 유입 속도가 처리 속도를 순간적으로 초과할 때 — 큐가 완충.
- 한 이벤트를 여러 소비자가 각자 처리할 때 — pub/sub.

## 전달 보장

- **at-most-once**: 유실 가능, 중복 없음. 드물게 씀.
- **at-least-once**: 유실 없음, 중복 가능. 실무 기본값 — 그래서 소비자
  멱등성이 필수다.
- **exactly-once**: 일반 분산 환경에선 사실상 불가. "at-least-once +
  멱등 소비자"로 같은 효과를 만든다.

## 멱등성

- 같은 메시지를 두 번 처리해도 결과가 한 번과 같게.
- 기법: 자연 멱등 연산(SET, upsert)으로 설계, 또는 처리 완료 ID를
  저장하고 중복 도착 시 스킵 (unique 제약이 최후의 방어선).
- 외부 효과(결제, 이메일)는 멱등 키를 외부 API에 전달 (idempotency key).

## 백프레셔

- 큐 깊이에 상한. 초과 시: 유입 거부(429/503 + Retry-After), 셰딩(낮은
  우선순위 버림), 또는 생산자 블로킹.
- 무한 큐는 장애를 숨기다가 OOM과 몇 시간짜리 지연으로 터뜨린다.
  큐 깊이는 항상 모니터링 + 알람.

## Outbox 패턴

- 문제: "DB 커밋 + 큐 발행"은 원자적이지 않음 — 커밋 후 발행 실패하면
  이벤트 유실.
- 해법: 이벤트를 같은 트랜잭션으로 outbox 테이블에 저장, 별도 릴레이가
  읽어 큐로 발행 (at-least-once). 소비자 멱등성과 한 세트.

## 작업 흐름 설계

- 단계 사이는 메시지/파일 계약으로만 통신 — 워커 교체·재시도·스케일이
  독립적이 됨.
- 재시도는 지수 백오프 + 최대 횟수 + DLQ(dead letter queue). DLQ 쌓이면
  알람 — 조용히 버리지 말 것.
- 긴 파이프라인은 각 단계가 재개 가능(resumable)하게: 중간 산출물을 남기고
  이미 완료된 단계는 스킵.
