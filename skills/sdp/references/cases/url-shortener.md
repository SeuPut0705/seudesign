# 케이스: URL 단축기

## 요구사항

- 기능: 긴 URL → 짧은 코드 생성, 코드 접속 시 리다이렉트, (선택) 통계.
- 비기능 가정: 쓰기 1천만/일 ≈ 115 RPS, 읽기:쓰기 = 100:1 → 읽기 ~11,500 RPS
  (피크 ~5만). 리다이렉트 p99 < 50ms. 코드는 영구 보존.

## 추정

- 저장: 항목 ~500B × 1천만/일 × 5년 ≈ 9TB. 복제 3배 ≈ 27TB — 단일 노드
  초과, 하지만 5년 뒤 얘기. 시작은 단일 PostgreSQL + 성장 시 샤딩 계획.
- 읽기 5만 RPS는 DB 직행 불가 — 캐시 필수.

## 핵심 설계 결정

**1. 코드 생성 — 후보 비교**

| 방식 | 장점 | 단점 |
|---|---|---|
| 전역 카운터 + base62 | 짧고 충돌 없음 | 발급점이 SPOF, 순번 노출 |
| 해시(URL) 잘라쓰기 | 무상태 | 충돌 처리 필요, 같은 URL 같은 코드 |
| 난수 + unique 재시도 | 단순, 예측 불가 | 공간 차면 재시도 증가 |

- 선택: **난수 7자리 base62** (62^7 ≈ 3.5조 — 5년치 182억의 0.5%, 충돌
  희박) + DB unique 제약으로 재시도. 발급 서비스 무상태 유지.

**2. 리다이렉트 경로 (읽기 지배적)**

```
클라이언트 → LB → 앱(무상태) → Redis (cache-aside, TTL+지터)
                                └miss→ PostgreSQL
```

- 인기 URL은 지프 분포 — 상위 소수가 트래픽 대부분. 캐시 적중률 90%+
  기대. 301(영구, 브라우저 캐시) vs 302(통계 수집 가능) — 통계 요구 있으면 302.

**3. 통계 (선택 기능)**

- 리다이렉트 경로에서 동기 집계 금지 — 클릭 이벤트를 큐로 발행, 워커가
  배치 집계. 리다이렉트 지연 보호가 우선.

## 확장 경로

1. 지금: 단일 PG + Redis + 무상태 앱 2대.
2. 읽기 증가: Redis 클러스터 + 읽기 복제본.
3. 저장 한계 도달: 코드 기반 해시 샤딩 (코드가 랜덤이라 균등 분포 —
   좋은 샤드 키).

## 면접 관문

- 읽기:쓰기 비율을 먼저 말하는가. 캐시 없이 5만 RPS를 DB로 보내지 않는가.
- 301/302 트레이드오프. 코드 생성의 충돌·SPOF 논의.
