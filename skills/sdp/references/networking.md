# 네트워킹과 통신

## DNS

- 도메인 → IP 해석 계층. 결과는 TTL 동안 캐시(브라우저, OS, 리졸버).
- 라우팅 정책: 가중치(카나리 배포), 지연 기반(가까운 리전), 지리 기반
  (규제·언어), failover(헬스체크 실패 시 보조로).
- DNS는 저렴한 글로벌 트래픽 분배기지만 반응이 느리다 — TTL만큼 낡은
  응답이 남는다. 빠른 전환이 필요하면 TTL을 미리 낮춰두거나 LB 계층에서
  처리.
- 함정: 클라이언트/리졸버가 TTL을 무시하기도 함 — DNS 전환만으로 즉시
  100% 이동한다고 가정하지 말 것.

## TCP vs UDP

| | TCP | UDP |
|---|---|---|
| 보장 | 순서, 재전송, 흐름 제어 | 없음 (fire-and-forget) |
| 비용 | 핸드셰이크, 상태 유지 | 최소 |
| 용도 | 웹, API, DB — 정확성 우선 | 스트리밍, 게임, VoIP, DNS 조회 — 지연 우선 |

- 기본값은 TCP. UDP는 "늦은 데이터는 버리는 게 낫다"일 때 (재전송된 옛
  프레임은 쓸모없음).
- HTTP/3(QUIC)는 UDP 위에 신뢰성을 직접 구현 — 연결 설정 왕복 감소.

## RPC vs REST

| | REST | RPC (gRPC 등) |
|---|---|---|
| 모델 | 리소스 + HTTP 동사 | 함수 호출 |
| 계약 | OpenAPI (선택적) | IDL 강제 (protobuf) — 타입 안전 |
| 직렬화 | JSON (사람이 읽음) | 바이너리 (작고 빠름) |
| 적합 | 공개 API, 브라우저 클라이언트 | 내부 서비스 간 고빈도 호출 |

- 흔한 균형: 외부는 REST, 내부 마이크로서비스 간은 gRPC.
- RPC의 함정: 네트워크 호출이 함수처럼 보여서 부분 실패·지연을 잊게 만든다
  — 모든 원격 호출에 타임아웃·재시도 정책은 여전히 필수.

## 연결 유지 vs 폴링 (실시간성)

| 방식 | 특성 |
|---|---|
| short polling | 주기 요청. 단순, 지연 = 주기, 빈 응답 낭비 |
| long polling | 서버가 이벤트까지 응답 보류. 지연 좋음, 연결 재수립 비용 |
| WebSocket | 양방향 상시 연결. 최저 지연, 연결 = 서버 상태 (확장 시 고려) |
| SSE | 서버→클라 단방향 스트림. 알림/피드 갱신에 가볍고 충분 |

- 선택 기준: 양방향 필요(채팅) → WebSocket. 서버 발 알림만 → SSE.
  수 분 단위 갱신이면 폴링으로 충분 — 상시 연결은 공짜가 아니다.
